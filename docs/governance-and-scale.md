# Governance and Scale

This document is the implementation contract for roadmap Phases 4 and 5. A capability is complete only when its API and persistence are tenant-isolated, authorization and negative-path tests pass, audit events are emitted, the operator workflow is documented, and the production dependency has been exercised.

## Phase 4 Control Plane

Organization administration owns tenant settings, workspace lifecycle, membership, and versioned role templates. Administrative writes require explicit permissions and immutable audit records; disabling the last tenant owner must be rejected.

Policy packs are immutable once published. A new change creates a new version. Every evaluation records the exact pack version, matched rules, decision, principal, resource, and correlation ID. Deny takes precedence over approval and allow; simulation uses the same evaluator but cannot execute an action.

Audit exports are asynchronous, tenant-scoped, time-bounded artifacts. Completed exports include record count and SHA-256 digest, use short-lived download authorization, and generate request, completion, download, and expiry audit events. Export workers must stream records rather than load a tenant history into memory.

Governance policies cover memory, audit events, transcripts, and task artifacts. Retention deletion is idempotent, legal hold takes precedence, and residency restrictions constrain both primary storage and exports. Organization approval rules may increase risk or require additional approvers, but cannot weaken a platform-level deny.

Enforcement today: the agent runtime's `ToolPolicy` consults the tenant's enabled approval rules and the rules of its active policy pack versions on every evaluation (planning, execution, recovery); a `deny` blocks, approval rules and `require_approval` pause the call for approval at any risk level, and `allow` changes nothing. The approve route enforces a matching rule's `required_roles` and `minimum_approvers`, or, for a rule with an AED band or approver steps, its [approval routing](approvals-and-risk.md#approval-routing). Patterns, conditions and the evaluation order are in [Approvals and risk](approvals-and-risk.md#organization-approval-rules-and-policy-packs). Policy pack simulation and a separate evaluation log are not built; the run's `tool_proposal` step records the matched rules and pack versions.

## Phase 5 Control Plane

Marketplace packages use immutable semantic versions, content digests, publisher signatures, requested scopes, review state, and revocation. Installation requires an administrator to grant a subset of requested scopes. Revocation prevents new execution without erasing historical evidence.

Regional placement records a tenant home region, allowed regions, residency mode, and failover policy. Requests must carry tenant and correlation context across regions. Automatic failover is permitted only to an allowed region and requires measured recovery-point and recovery-time objectives.

Model routing policies constrain provider, model, region, data classification, latency, and per-run cost. Each routing decision is auditable and records reason codes. Fallback may not bypass policy, residency, budget, or model allowlists.

Enterprise operations include tenant/workspace budgets, throttling, service-level objectives, regional health, incident records, queue age and dead-letter visibility, controlled replay, and break-glass actions with expiry and mandatory audit review.

## Who may change what

Governance settings are tenant-level: one policy pack, role template, approval rule, memory governance setting, organization model budget, routing target, marketplace catalog package or published skill version binds (or is offered to) every workspace of the organization. Changing them therefore needs the tenant-level permission `organization_policy:manage` (`Permission.ORG_POLICY_MANAGE`), which only the organization role `org_admin` grants (`anum_api/authorization.py`, `OrganizationRole`). No workspace role grants it, not even `owner`: owning one workspace is not enough to change policy for all the others.

A refused change answers `403` with `Organization administrator role required: this setting applies to every workspace in the organization, so owning a workspace is not enough. Ask the administrator of your ANUM sign-in (Keycloak) to assign you the realm role org_admin (on a self-hosted server: infra/oracle/keycloak-2fa.sh grant-org-admin <your username>), then sign out and sign in again`, writes nothing and records no audit row. `GET /organization/governance` also returns `can_manage_organization_policy`, the API's answer for the caller, so clients do not guess from the workspace role; the web Governance and Enterprise views and the Flutter Organization screen use it to show policy packs, routing targets and the catalog read-only with an explanation. `GET /model-budgets` returns `can_manage_tenant_budget` the same way for the organization budget card (web Budgets view, Flutter Model budgets screen).

Where `org_admin` comes from:

- `ANUM_AUTH_MODE=oidc`: the Keycloak realm role `org_admin` in the access token (`realm_access.roles` or `roles`). Unlike the workspace realm roles, which the persisted membership replaces, it is kept next to the membership role, and it applies only to the token's IdP-managed `tenant_id`. Grant it in Keycloak to the organization's administrators ([Identity: Organization administrators](identity.md#organization-administrators)). The caller still needs an active membership in the request's workspace. Nobody holds it after an upgrade: Keycloak imports the realm only on its first start, so an existing realm first needs the role created and assigned (Oracle: `keycloak-2fa.sh grant-org-admin <username>`; Render: the admin console). Until then every change listed above answers `403`, the deployment's owner included; the web Governance view shows the same instructions in its read-only notice.
- `ANUM_AUTH_MODE=headers` (local and test only): `x-user-roles` containing `org_admin`, for example `owner,org_admin`. Local development sessions (`/api/v1/auth/local/*`) carry it, like the realm's DEV-ONLY `dev` user.

Organization administrators also read and export the [audit log](#audit-log) of every workspace they are a member of, and may rename, archive, restore and create workspaces ([Identity: Workspace lifecycle](identity.md#workspace-lifecycle)).

Not built yet: managing organization administrators inside ANUM (they are managed in the identity provider). The web publishes skill versions (Skills) and marketplace packages (Enterprise) for organization administrators; Flutter does not. `routing:manage` is still granted to workspace owners but no route checks it any more.

## Policy packs

A policy pack is a named, versioned list of rules (`action` pattern, `effect` `allow`, `require_approval` or `deny`, optional `conditions` object) that the runtime's `ToolPolicy` evaluates for every workspace of the tenant. Versions are immutable: `POST /policy-packs` with an existing name archives that pack's active version and stores the next number as the active one, so the history is never edited in place. `POST /policy-packs/{id}/archive` takes a version out of enforcement, `/activate` brings it back (one active version per name), and `DELETE /policy-packs/{id}` removes an archived version for good (`409` while it is active: "Archive it first, then delete it."; the versions that stay keep their numbers and the next publish continues after the highest one left). Every change is audited (`policy_pack.created`, `.activated`, `.archived`, `.deleted` with the name, version and rule count).

Web (Governance, `apps/web/src/EnterpriseViews.tsx`, `PolicyPackEditor.tsx`): packs are shown one group per name with the active version's rules, a count of versions and a search box (name, description, rule action or effect) with "N of M packs shown" and "Show more" paging ten groups at a time. **New policy pack** opens the editor: start from a blank pack or from the **Organization baseline** (a translated template: high-risk integration writes and payments wait for approval, deleting memories is denied), name, description and a rules table with add, remove and move up or down; conditions are typed as JSON and refused in place when they are not an object. **New version** opens the same editor on the active version of a group and publishes the next number. Each group expands to its version list (published when, rule count, Active or Archived) with Activate or Archive and, for archived versions, Delete behind a confirmation; **Compare versions** puts two versions side by side and marks each rule Added, Removed, Changed (with the previous rule struck through) or Unchanged. Everyone else sees the same lists read-only with the notice that says who can change them; the empty state tells an administrator to publish the first pack and everyone else who does. Tests: `services/api/tests/test_governance.py`, `test_postgres_governance_depth.py`, `apps/web/test/governance.test.ts`, `apps/web/e2e/governance.spec.ts`.

## Role templates

A role template is a named set of permission names (`POST /role-templates`, unique per tenant, case-insensitive). It does a job once a workspace owner gives it to a member: `PUT /workspace-members/{user_id}/role-template {"role_template_id": "..."}` copies the template's permissions onto the membership (`workspace_memberships.role_template_id` and `permission_limit`, migration `0166_governance_depth`), and from that person's next request their **effective permissions are their workspace role's permissions intersected with the template's**. Permissions the template names that the role does not grant never apply (a viewer with a `task:run` template stays read-only), so a template can only narrow a role, never widen it. Owners cannot carry a template (`409`: change the role to member or viewer first), and promoting a templated member to owner drops it; `{"role_template_id": null}` takes a template away. A request the template does not cover answers `403 Workspace permission denied: your role template does not include this permission. A workspace owner can assign you another template, or none, in Members`. The limit is read with the membership (`TenantContext.permission_limit`) in `oidc` mode and, for local header authentication, from the stored membership when there is one. Templates have no edit or delete route, so the copy on the membership never drifts from the template. `GET /workspace-members` carries `role_template_id`, `role_template_name` (null if the template no longer exists) and `effective_permissions` (null without a template). Audited as `workspace_member.role_template` (previous and new template id, the permission list) and `workspace_member.role_change` with `role_template_cleared` when a promotion dropped one.

Web: Governance lists the templates with search (name or permission) and paging, says how they are used and links to Members; Members shows, under each member or viewer, a **Role template** select (None, or one of the tenant's templates) that asks for confirmation and then says how many permissions apply and which of the template's permissions are outside the role and do not. Owners' rows say that owners keep the whole owner role. Tests: `services/api/tests/test_governance.py` (narrowing, removal, owners, promotion, a viewer's effective set), `test_postgres_governance_depth.py` (the columns under RLS, enforcement on the next request), `apps/web/e2e/admin.spec.ts`.

## Memory governance

`GET` and `PUT /organization/memory-governance` hold one tenant-wide setting: `default_retention_days` (1 to 3650), `allow_permanent_retention`, `require_provenance` and `allowed_source_types` (at most 50; empty allows every source; `conversation` lets the Assistant remember from chats, [Memory](memory.md#conversation-memory)). `GET` answers `404` until an organization administrator saves it. Web (Governance, `apps/web/src/MemoryGovernanceCard.tsx`): the card shows who saved it and when, or that it is not saved yet and that memories follow the suggested values shown; administrators edit and save it from the same card (values validated like the API), everyone else reads the four values. The Flutter Organization screen has the same card.

## Routing targets

A routing target (`PUT /routing/targets/{id}`) names a region, provider, model, modalities, sensitivity levels, cost per 1k tokens, a nominal latency and whether it is **in routing** (`enabled`, default true; off: `POST /routing/decisions` and the figures skip it). Health is no longer typed by hand. A status sent with `PUT` is only a hint until the **probe** measures the target; the probe's own columns (`last_checked_at`, `measured_latency_ms`, `last_error`, `probe_workspace_id`; migration `0166_governance_depth`) are never taken from a request, stay while the target's provider and model are unchanged, and are reset ("not yet probed") when either changes.

`POST /routing/targets/{id}/probe` (`anum_api/routing_probe.py`) sends the model connection test's prompt to the target's model through the **calling workspace's model configuration** (Settings, Model: its base URL and key, with the egress guard), with no transaction open during the call, and stores what it measured: `healthy` (answered; `measured_latency_ms`), `degraded` (the provider answered with an error, or the answer took `ANUM_ROUTING_PROBE_DEGRADED_MS` or more, default 10000), `offline` (not reachable; `last_error` worded like the connection test, generic outside local and test) or `unverified` with a `last_error` that says the workspace has no configuration for the target's provider (or one for another provider) and what to do. The `mock` provider always answers. Probing the built-in `configured-model` stores it as a tenant target. Probed, enabled targets are re-probed on the automation scheduler (`ANUM_AUTOMATION_SCHEDULER_ENABLED`; pass `routing_probe`) once they are older than `ANUM_ROUTING_PROBE_INTERVAL_SECONDS` (default 900), at most `ANUM_ROUTING_PROBE_BATCH_SIZE` (50) per pass, each with the model configuration of the workspace that probed it last: with PostgreSQL the due targets are discovered as `anum_maintenance` (`tenant_id`, `id`, `probe_workspace_id`, `last_checked_at`, `enabled` only, policy `maintenance_routing_probe`) and each probe runs as the application role inside that tenant and workspace. A target the scheduler never saw probed is never probed by it. Audit: `routing_target.saved`, `routing_target.probed` (every on-demand probe, and a scheduled one only when the status changed; actor `system:routing-probe` for the schedule), `routing_target.deleted`.

`DELETE /routing/targets/{id}` removes a tenant target. It answers `409` while the target is **in use** (in routing and its last probe found it `healthy` or `degraded`: "Take it out of routing first, then delete it."), and `409` for the deployment's built-in configured model, which comes from the server's model settings. `GET /enterprise/operations` counts **probed** targets only: `healthy_targets`, `degraded_targets`, `active_regions` and `failover_ready` (healthy targets in more than one region) ignore a typed status, and `unprobed_targets` (in routing, never probed) and `disabled_targets` say what is left out.

Web (Enterprise): the target table shows a Health column (Not yet probed, healthy, degraded, offline or Out of routing, with the measured latency and time or the last error), the measured cost and latency, and per row Probe now, Take out of routing or Put back in routing, Edit and Delete (disabled, with the reason, while the target is in use; a confirmation otherwise; the API's `409` is shown in place). The form has no status field, only the In routing switch; the figures say "N not yet probed" and the failover figure is "Unknown" until something was probed. Below 1100px the region and model columns move under the target id and the four row actions sit two by two. The Flutter Organization screen shows the same health and offers Probe now and Take out of or Put back in routing. Tests: `services/api/tests/test_phase5.py` (probe outcomes, the kept and reset probe result, delete and the in-use check, the scheduler pass), `test_postgres_governance_depth.py` (persisted probe columns, the maintenance role's view, the pass on PostgreSQL), `apps/web/test/governance.test.ts`, `apps/web/e2e/governance.spec.ts`, `apps/mobile/test/governance_screen_test.dart`.

## Persistence

With `ANUM_REPOSITORY_BACKEND=postgresql` policy packs, role templates, approval rules and memory governance are tenant-level tables, the marketplace catalog (`marketplace_packages`) and routing targets are per tenant, and marketplace installs are per workspace, all under RLS ([Multi-tenancy](multi-tenancy.md#control-plane-stores)). Every governance write records an `audit_records` row (append-only: RLS allows select and insert only) in the same transaction, so a rejected write leaves no audit record; `GET /audit/export` returns the acting workspace's audit trail, which also includes membership, workspace and privacy changes. With `ANUM_REPOSITORY_BACKEND=memory` governance audit records go to the same in-process store as every other audit record, so the log and the export show them together there too. Packages published with `PUT /marketplace/packages/{id}` (organization administrators) are visible only to the publishing tenant.

## Audit log

Every audited change in a workspace (members, invitations, workspace lifecycle, policy packs and other governance settings, model budgets, approval policy, privacy export and deletion, developer mode, and the audit export itself) is an append-only row in `audit_records`: id, actor (user id), action, target, outcome, correlation id, time and metadata (ids, counts and settings; keys that look like secrets are stored as `[REDACTED]`). RLS allows select and insert only, for the request's tenant and workspace. Implemented in `services/api/anum_api/audit_log.py`.

| Route | Effect |
| --- | --- |
| `GET /api/v1/audit-records?actor=&action=&target=&outcome=&correlation_id=&since=&until=&q=&limit=&cursor=` | One page, newest first (`created_at`, then id, descending): `{items, next_cursor, retention}`. `action` matches exactly or, ending in `*`, as a prefix (`workspace_member.*`; LIKE wildcards are literal). `since` is inclusive and `until` exclusive (ISO 8601, UTC when no offset; `since >= until` answers `422`). `q` matches actor, action or target as a case-insensitive substring. `mention` (repeatable, at most 100 distinct ids of at most 200 characters, else `422`) keeps records whose actor or target equals one of the ids or whose metadata holds one of them as a value at any depth (exact match, no substring); the headquarters History panel uses it to export one room with its desks, or one agent ([History panel](ANUM_MINE_HQ_HISTORY_PANEL.md)). `limit` 1 to 200 (50 default). `next_cursor` is an opaque keyset cursor; an invalid one answers `400`. |
| `GET /api/v1/audit-records/actions` | The distinct actions recorded in this workspace (at most 500), for the action filter. |
| `GET /api/v1/audit-records/{id}` | One record of this workspace, else `404` (another workspace's record is not found). |
| `GET /api/v1/audit/export?format=json\|csv&<same filters>` | The filtered range, newest first, as a JSON array or CSV (`id, created_at, actor, action, target, outcome, correlation_id, tenant_id, workspace_id, metadata` with metadata as JSON). File name `audit-<workspace>-<UTC time>.<format>` in `Content-Disposition`. |

- **Who.** Workspace owners (`audit:read`, `audit:export`) and organization administrators (`org_admin`) with an active membership in the workspace, whatever their role there. Everyone else gets `403` with "Audit log access requires the owner role in this workspace or the organization administrator role. Ask a workspace owner to show you the log or change your role." Reads always run in the caller's tenant and workspace RLS scope, so the log and the export never include another workspace's records.
- **Export.** Recorded as `audit.export` (format and filters, including any `mentions`) in the request's transaction before the body is sent. The body is streamed in batches of 500, each read through its own short read-only transaction in the caller's RLS scope (never the request's session, which is closed by then), so a large log is not held in memory; the range is pinned to the request time, so the export does not include itself or later records. CSV cells that start with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with `'` so spreadsheets do not run them as formulas. The file is produced synchronously; the asynchronous export with digest and expiring download described in [Phase 4](#phase-4-control-plane) is not built.
- **Coverage.** Every state-changing route (POST, PUT, PATCH, DELETE in the OpenAPI schema) of the email, WhatsApp, autonomy, developer-mode, learning, automation and custom agents APIs writes at least one audit record, and none copies a secret or the text the request carried. Each module's test file walks all of its routes through `services/api/tests/audit_probe.py`, which fails on a successful call without a record and on a route the walk did not exercise; `tests/test_audit_coverage.py` checks every module has a walk and that the few exemptions (a schedule preview and a project name match that store nothing, the WhatsApp per-view read marker, Meta's signed webhook deliveries and signed automation webhook deliveries, whose runs are in the run history) name real routes with a reason.
- **Retention.** Audit records are kept for as long as the workspace exists, including after it is [archived](identity.md#workspace-lifecycle); no retention job purges them and nobody can edit or delete them, owners included. The API returns this text as `retention` and both clients show it under the log. A configurable audit retention period and legal hold are not built.
- **Indexes.** `(tenant_id, workspace_id, created_at)` plus, from migration `0028_workspace_admin` (built concurrently), `(tenant_id, workspace_id, actor, created_at)` and `(tenant_id, workspace_id, action, created_at)` for the actor and action filters.
- **Web.** Audit log in the navigation (`apps/web/src/AuditLogView.tsx`, logic in `src/lib/audit.ts`): search, actor, action (the recorded actions plus "any" per family), target, outcome and a From/To day range (local days; To is inclusive, sent as the next day's start), Apply and Reset; a table (stacked rows below 760px) with "Load older records" (keyset); each row's time opens a detail drawer (dialog with focus moved in, Tab kept inside, Escape and Close return focus to the row) with every field and the metadata, and "Only this actor", "Only this target" and "Same correlation id" to narrow the log. Export CSV and Export JSON download the filtered range. Loading, error with Try again, permission denied (who can read it, and the API's words), empty (with Reset filters or, for an empty log, a way to Members) and the retention note are all shown.
- **Flutter.** Settings › Workspace administration › Audit log (`apps/mobile/lib/features/admin/audit_log_screen.dart`): read-only on the phone. Search, action and a date range, "Load older records", a detail sheet per record, and the same states. Filtered export is web-only; the Organization screen exports the whole log (JSON or CSV).
- Tests: `services/api/tests/test_audit_log.py` (paging, filters, detail scoping, permissions, export filters and its own audit record, CSV formula neutralising, more than one export batch), `test_postgres_audit_log.py` (the same under RLS as the app role, LIKE wildcards, batches through their own sessions), `apps/web/test/audit.test.ts`, `apps/web/e2e/audit.spec.ts` (paging, keyboard on the drawer, filters sent to the API, export file name, empty, error and denied states, layout at 1440x900, 1366x768, 1024x768, 768x1024 and 390x844) and `apps/mobile/test/audit_admin_test.dart` (paging, filters, detail, denied and empty states, 320 to 1440 wide at 200% text).

## Shared Contracts

The TypeScript definitions in `packages/contracts/src/governance.ts` are transport-neutral control-plane contracts. Backend schemas and client types should preserve their field semantics. Secrets, access tokens, raw credentials, and provider keys must never appear in these resources or their audit payloads.

## External Readiness Gates

Production completion requires identity-provider administration, an object store with lifecycle policy, signing-key custody, at least two deployed regions, a replicated persistence design, provider credentials, production telemetry, alert delivery, and an approved incident/disaster-recovery process. Source code alone cannot satisfy these gates.

## Web console

The web app's Governance view lists every policy pack (grouped by name with its versions), the role templates, the organization approval rules and the memory governance card to every member, each list with search and paging. Organization administrators (`can_manage_organization_policy`) publish packs and new versions from the editor, activate, archive or delete versions, create role templates, add, edit and delete approval rules and save memory governance; everyone else, a workspace owner included, sees the same lists read-only with a notice that these settings apply to every workspace, so only an organization administrator can change them, and whom to ask. A `403` on a change is shown in place with the API's message. Tests: `apps/web/test/governance.test.ts` (`organizationPolicyAccess`) and `apps/web/e2e/governance.spec.ts`. The Enterprise view reports regions from the configured routing targets only: with zero or one serving region it says so ("Single region", failover "Not applicable") instead of a pending failover. Routing targets are tenant-wide, so only organization administrators create and edit them (`PUT /routing/targets/{id}`); the view loads `can_manage_organization_policy` from `GET /organization/governance` and, for everyone else, hides the add and edit controls and says why (read only: only an organization administrator can change routing targets or publish to the marketplace catalog, and how to get the role). If that capability check fails the page still shows the targets and catalog, read-only, with the error. Installing a catalog package into this workspace stays a workspace-owner action, so the Install button shows only for owners.

### Marketplace

The Enterprise view's marketplace catalog (`apps/web/src/MarketplaceCatalog.tsx`) searches id, name, publisher and permissions, filters by kind, "Verified only" and "Installed here", lists installed packages first and pages 20 at a time. Install opens a summary of what the owner grants: kind, version and publisher, each permission requested, regions, and a warning when the publisher is not verified; uninstall asks for confirmation. Organization administrators publish, edit and delete packages from a form that validates like the API; deleting a package installed in any workspace answers `409` and the message says so. `GET /marketplace/packages` takes `kind`, `verified` and `q`. Package fields are validated (id `^[a-z0-9][a-z0-9_.-]{1,79}$`, semantic version, at most 50 permissions and 20 regions). Publishing, updating, deleting, installing and uninstalling are audited in the same transaction (`marketplace.package_published`, `marketplace.package_updated`, `marketplace.package_deleted`, `marketplace.package_installed` with the granted permissions, `marketplace.package_uninstalled`; target `marketplace_package:{id}`). An install records the workspace's adoption and nothing more: it adds no tools or skills (skills are installed under Skills, integrations set up under Integrations), and the catalog and the install dialog say so in both languages (`market.recordOnly`). Tests: `services/api/tests/test_skill_catalog.py`, `apps/web/test/catalog.test.ts`, `apps/web/e2e/marketplace.spec.ts`, `apps/web/e2e/governance.spec.ts`. Routing targets are probed, taken out of routing and deleted as described in [Routing targets](#routing-targets); the table stays readable at 1440x900, 1366x768, 1024x768, 768x1024 and 390x844 (`apps/web/e2e/governance.spec.ts`). The Integrations view gives owners test connection, a per-workspace switch and, for the external REST webhook, an encrypted workspace token ([Tools and integrations](tools-and-integrations.md#workspace-configuration)). Health checks honor only the enabled flag: they always probe, and report, the operator-configured endpoint from Settings, never a workspace-saved one (SSRF).

### Package signing

Marketplace packages of kind `integration` are signed and verified like skill versions ([Skills: Signing](skills.md#signing)), against the same trusted publisher and platform keys. The digest is the SHA-256 of canonical JSON `{"format": "anum-integration-v1", "id", "kind", "name", "permissions", "publisher", "regions", "version"}` (keys sorted, no whitespace, UTF-8, permissions and regions sorted and de-duplicated); the signature is Ed25519 over `anum-integration-signature-v1`, a line feed and the digest's hex, so a skill signature can never stand in for a package one. `PUT /marketplace/packages/{id}` takes an optional `signature`; a new signature that does not verify is refused with `422` and audited (`marketplace.signature_refused`). Because a package can be edited, a change that keeps the old signature stores the package with `verification.status == "invalid"`. `PUT /marketplace/packages/{id}/signature` attaches a signature later (`422` for skill packages, `409` when it already verifies). Installing an unsigned or unverifiable integration answers `409 Package {id} {version} cannot be installed: ...` and is audited (`marketplace.install_refused`). `GET /marketplace/packages` and `GET /marketplace/installs` carry `verification`; installs also carry `disabled_reason`. Revoking a key flags integration installs it signed and, with automatic disabling on, turns them off in every workspace. The web catalog shows the signer, disables Install with the reason, flags and explains turned-off installs, asks for confirmation before turning a flagged one back on, and lets organization administrators attach a signature. Tests: `services/api/tests/test_skill_auto_disable.py`, `test_postgres_skill_signing.py`, `apps/web/e2e/marketplace.spec.ts`.
