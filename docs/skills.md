# Skills

Skills are reusable capability packages that guide ANUM agents through a class of work. A skill may include instructions, schemas, example workflows, tool requirements, validation rules, and risk metadata. Skills should improve reliability without bypassing runtime policy.

## Skill Contents

A skill should be declarative where possible. It can define purpose, trigger conditions, required tools, input schema, output schema, allowed memory scopes, approval requirements, and test cases. Implementation code should live in normal application packages or tool adapters, not hidden inside a skill document.

## Loading and Selection

The runtime should select skills based on task intent, tenant policy, user permissions, and tool availability. Skill selection should be recorded in the task trace so users and developers can understand why an agent behaved a certain way.

## Safety

Skills are not trusted code by default. They should not grant access to tools or memory. They can request capabilities, but the runtime and authorization layer decide what is actually available. Skill updates should be versioned and auditable.

## Repository Placement

The monorepo should eventually include a `skills/` workspace for first-party skill definitions, examples, and tests. Skill packages should avoid secrets and environment-specific configuration.

## Implemented Control Plane

The Phase 2 API provides immutable semantic versions, tenant-owned publishing, workspace installations, declared and administrator-approved tool grants, and execution-time resolution. Resolution intersects the installed grants with runtime tool availability and rejects skills above the caller's risk ceiling. Skill instructions never grant tools by themselves.

Endpoints are under `/api/v1/skills`: `POST /versions`, `PUT /versions/{skill_id}/{version}/signature` and `/publisher-keys` ([Signing](#signing)), `GET /versions` (`q` matches skill id, name or description; `limit` up to 500 and `offset` page it), `GET /{skill_id}` (details), `POST /installations`, `GET /installations`, `PATCH|DELETE /installations/{skill_id}`, `POST /installations/{skill_id}/rollback`, and `POST /resolve`. A published version belongs to the tenant and can be installed in every workspace, so `POST /versions` needs the organization administrator role `org_admin` (`organization_policy:manage`, [Governance](governance-and-scale.md#who-may-change-what)); a workspace owner without it gets `403` and nothing is published. Installing, enabling, disabling and uninstalling stay workspace-owner actions (`policy:manage`), and every member can read versions, installations and details.

- **Details (`GET /skills/{skill_id}`, any member).** Versions newest first, this workspace's installation, and `tools`: each tool the shown version requires, as this runtime treats it: whether it is registered here, its description, `risk_level`, `approval` (`always` for high risk, `policy` for medium when the workspace approval policy covers it, `rule` for low unless an organization approval rule or policy pack asks, `blocked`, or `unavailable` when the deployment does not have the tool), the integration host it contacts, and whether the installation granted it. `?version=` describes another version (what installing it would grant). `history` is the skill's audit trail in this workspace (newest first, at most 50), and `can_manage` / `can_rollback` are the caller's rights.
- **Rollback (`POST /skills/installations/{skill_id}/rollback {"version"}`, organization administrators: `organization_policy:manage`).** Moves the installation to an earlier published version (`422` for the same or a newer one: install that instead). Grants never widen: the installation keeps only the tools it had already granted that the earlier version also declares. The enabled switch is kept.
- **Audit.** Publishing (`skill.published`), installing (`skill.installed`, with `previous_version` when it replaced one), enabling, disabling, uninstalling and rolling back are each written to `audit_records` in the same transaction as the change, target `skill:{skill_id}`; the audit export includes them.
- **Clients.** The web Skills page (`apps/web/src/SkillsView.tsx`) lists one card per skill (installed version, tools, risk, state, "upgrade available"), with search over id, name, description and tools, an All / Installed / Not installed filter and "Show more" paging (12 at a time). Details open in a dialog with the tools table, versions, history and, for organization administrators, "Roll back to" with confirmation; owners install (a review dialog lists each tool's risk and approval before granting), upgrade, enable, disable and uninstall. Organization administrators publish versions from a form that validates like the API. Members and non-admin owners see why controls are missing. Flutter Resources > Skills installs, enables, disables and uninstalls (with confirmation), shows the installed version, and says who can act when the API refuses. Tests: `services/api/tests/test_skill_catalog.py`, `test_postgres_integration_state.py`, `apps/web/test/catalog.test.ts`, `apps/web/e2e/skills.spec.ts`, `apps/mobile/test/skills_resources_test.dart`.

## Agents that load a skill

An installed skill does its work through [agents](agents.md#skills): an agent that allows it loads the installed version's instructions into every task and chat while the installation is enabled and its tools are granted, registered and allowed on the agent. Disabling or uninstalling a skill stops that from the next run. The web Skills page shows, from `GET /api/v1/agents/skills/usage`, which agents (that the viewer can see) load each skill on its card and in its details, and asks for confirmation naming how many agents stop loading it before an owner disables or uninstalls it. Built-in runtime skills (from `GET /api/v1/agents/catalog`) are listed in their own "Built into ANUM" section with a Built in filter: nothing to install, loaded by agents when their tools are allowed.

With `ANUM_REPOSITORY_BACKEND=postgresql` versions live in `skill_versions` (tenant-level, unique per tenant, skill and version) and installations in `skill_installations` (one per workspace and skill, referencing the installed version), both under RLS ([Multi-tenancy](multi-tenancy.md#control-plane-stores)). Trusted publisher keys live in `skill_publisher_keys` (tenant-level, forced RLS, migration `0082_skill_signing`).

## Signing

Every skill version is checked against an Ed25519 signature before anyone can install it, upgrade to it or roll back to it (`anum_api/skill_signing.py`).

- **Canonical package digest.** The SHA-256 of a canonical JSON document of the fields agents act on: `{"description", "format": "anum-skill-v1", "instructions", "name", "required_tools", "risk_level", "skill_id", "version"}` with keys sorted, no whitespace (`separators=(",", ":")`), raw UTF-8 (`ensure_ascii=False`) and `required_tools` sorted and de-duplicated. Text is signed exactly as stored. The signature is Ed25519 over the bytes `anum-skill-signature-v1`, a line feed, then the digest's lowercase hex, so a skill signature can never be replayed as anything else. Any change to a signed field changes the digest and breaks the signature.
- **Where trust comes from**, checked in this order: (1) **first-party**: a version whose content is a skill shipped in this release's blueprints (`anum_api/blueprints/*.json`; the tools may be the subset this server has, every other field must match) verifies without a signature, because the server already trusts its own code; setup plans publish these. (2) **Platform keys**: `ANUM_SKILL_PLATFORM_KEYS="key-id=BASE64,..."` (raw 32-byte Ed25519 public keys) for first-party skills signed outside ANUM; malformed entries are ignored with a warning, and tenants cannot register a key id a platform key uses. (3) **The tenant's trusted publisher keys**, managed by organization administrators.
- **Verification is computed on every read**, never stored, against the keys as they are now: `verification` on each version, installation and detail answer has `status` (`verified`, `unsigned`, `invalid`, `revoked`, `unknown_key`), `installable`, `digest`, `key_id`, `signer`, `key_source` (`tenant`, `platform`, `first_party`), `fingerprint`, `signed_at` and a `detail` sentence that says what to do.
- **Publishing.** `POST /skills/versions` takes an optional `signature: {"key_id", "signature"}` (base64). A signature that does not verify is refused with `422 Signature refused: ...` and nothing is published. A version may be published unsigned; an organization administrator attaches the signature later with `PUT /skills/versions/{skill_id}/{version}/signature` (`409` if it already verifies, `422` if the signature does not). The content never changes: the publisher signs the digest shown in `verification.digest` offline. ANUM never holds private keys.
- **Install, upgrade and rollback refuse** an unsigned or unverifiable version with `409` and the reason, for example `Skill acme.notes 2.0.0 cannot be installed: This version is not signed. An organization administrator signs it with a trusted publisher key before anyone can install it.` Rollback goes only to a previous signed version (`409 Cannot roll back to 1.5.0: only a signed version can be rolled back to. ...`).
- **Keys** (`/api/v1/skills/publisher-keys`): `GET` (any member; public keys only, plus `platform_keys` and `can_manage`), `POST {"id", "publisher", "public_key"}` (add), `POST /{id}/rotate {"new_id", "public_key"}` and `POST /{id}/revoke {"reason"}`, each for organization administrators (`organization_policy:manage`). Key ids match `^[a-z0-9][a-z0-9_.-]{2,79}$` and are never reused in a tenant; a public key already trusted, or once revoked, cannot be added again. **Rotation** makes the old key `rotated`: it keeps verifying what it signed before the rotation, and new signatures with it are refused. **Revocation** is final: versions signed with the key can no longer be installed, upgraded to or rolled back to, and installations of them are flagged (`verification.status == "revoked"`) in every workspace at once. What happens to installations already running depends on the tenant setting below.
- **Disable flagged installs automatically** (`GET`/`PUT /skills/signing-settings {"disable_flagged"}`, table `skill_signing_settings`; every member reads it, organization administrators change it, audited as `skill.signing_settings_updated`). **On by default.** When a key is revoked with it on, every enabled skill installation and integration install the key signed is turned off at once in every workspace of the tenant (`anum_api/skill_flagging.py`): the workspaces are found as `anum_maintenance` (scope, id, version and the enabled flag only), then each is changed in its own short unit of work as the application role inside that workspace's RLS context. The installation records `disabled_reason`, agents stop loading it from the next run (resolution needs an enabled installation), `skill.installation_disabled` or `marketplace.package_disabled` (outcome `flagged`) is audited in that workspace, and each owner of the workspace gets a `skill_signing` notification naming what was turned off. The revoke answer carries `auto_disable` and `disabled_installations`. With the setting off, installations stay on and only flagged. Rotation never turns anything off.
- **Turning a flagged installation back on is explicit**: `PATCH /skills/installations/{skill_id} {"enabled": true}` (and `PATCH /marketplace/packages/{id}/install`) answers `409 ... Confirm that you want to turn it on anyway.` unless the body also has `"acknowledge_flagged": true`; that is audited as `skill.flagged_reenabled` (`marketplace.flagged_reenabled`).
- **Audit**, in the same transaction: `skill.publisher_key_added`, `skill.publisher_key_rotated`, `skill.publisher_key_revoked` (with the reason, affected versions and flagged installations; target `skill_publisher_key:{id}`), and on the skill (`skill:{skill_id}`): `skill.published` and `skill.installed` with the digest, signer and status, `skill.signed`, `skill.installation_flagged` (outcome `flagged`), and refusals `skill.signature_refused`, `skill.install_refused`, `skill.rollback_refused` (outcome `denied`, committed before the error is returned).
- **Clients.** The web Skills page shows each card's signer and status, disables Install and Upgrade for a version that does not verify and says why, and flags an installation whose key was revoked. Details show each version's badge, digest (with copy), signer and fingerprint, offer rollback only to signed versions and let organization administrators attach a signature. The **Publisher keys** tab (`apps/web/src/PublisherKeysPanel.tsx`) has the "Disable flagged installs automatically" switch (read only for everyone but organization administrators), lists keys with search, a status filter and paging, lets organization administrators add, rotate (with confirmation of what happens) and revoke (with a reason), explains to everyone else who can, and shows the platform keys read only. Flutter Resources > Skills shows the signer and status read only, flags a revoked installation and disables Install for a version that does not verify.
- **Tests.** `services/api/tests/test_skill_signing.py` (canonical digest, tampering, unknown, rotated and revoked keys, refusals, rollback, platform and first-party trust, audit, migration), `test_skill_auto_disable.py` (integration packages, the setting, automatic disabling across workspaces with audit and owner notifications, explicit re-enabling), `test_postgres_skill_signing.py` (RLS, persistence and cross-workspace disabling under RLS), `apps/web/test/skillSigning.test.ts`, `apps/web/e2e/skill-signing.spec.ts`, `apps/mobile/test/skill_signing_test.dart`. Test keys are derived at runtime from a plain label (`tests/skill_signing_support.py`), never committed.

## Remaining Distribution Work

Organization-wide promotion workflows and quality scoring remain part of the distribution and production-hardening work. Marketplace packages of kind `integration` are signed the same way ([Governance: Package signing](governance-and-scale.md#package-signing)); packages of kind `skill` are not, because the skill itself is signed in the registry. A marketplace package of kind `skill` is not linked to the skill registry: installing it records the workspace's adoption only. Flutter has no skill details, rollback or publishing screen yet (web only).
