# Security

ANUM should be designed as a security-sensitive system from the beginning because agents can read private context, call external tools, and act on behalf of users. Security must be part of the product model, not an afterthought added around an autonomous core.

## Identity

Keycloak is the identity provider. ANUM uses OIDC for sign-in, token issuance, session management, MFA policy, and federation. Application services validate tokens, map external identities to ANUM users, and avoid embedding identity assumptions in client code. On shared Keycloaks every password sign-in needs a second factor (authenticator app or recovery code) and passkeys with user verification are accepted alone ([Two-factor sign-in](identity.md#two-factor-sign-in)).

The realm is code (`infra/keycloak/anum-realm.json`): public clients use authorization code with PKCE only, tokens carry `aud: anum-api` and an admin-managed `tenant_id` claim, and the API validates issuer, audience, expiry, and signature against a cached, rotation-aware JWKS. The persisted workspace membership, not the token's realm roles, decides the caller's workspace role. Development authentication (header-asserted context and `anum_local_*` sessions) is refused at startup outside `local`/`test`. The full contract is in [Identity and sign-in](identity.md).

## Authorization

ANUM authorization should combine application-level policy with PostgreSQL row-level security. The backend decides whether a user, service, or agent may perform an action. The database enforces tenant and workspace isolation so accidental query mistakes do not leak data across boundaries. Two narrowly privileged roles read across tenants, and neither is `BYPASSRLS`:

- The event outbox relay runs as `anum_outbox_relay`. It can read unpublished `domain_events` rows and update their publication columns, nothing else ([Events](events.md#relay-role-and-rls)).
- Maintenance jobs (automation scheduler, voice transcript purge, secrets rotation) discover work as `anum_maintenance`. It reads a few id and timestamp columns of rows that need work and cannot write. The work itself runs as the application role inside each tenant's RLS context ([Multi-tenancy](multi-tenancy.md#maintenance-role)).

Within one tenant, `anum_membership_reader` lists one user's own active memberships across the tenant's workspaces for `GET /api/v1/me/workspace-memberships`: a few columns, only rows of `anum.tenant_id` and `anum.user_id`, no writes, granted to the API login `WITH INHERIT FALSE` so its policies never widen the application role's own queries ([Multi-tenancy](multi-tenancy.md#membership-directory-role)).

### Virtual headquarters boundary

The current `#office-preview` is an illustrative browser view. `apps/web/src/main.tsx` renders it only inside `SignedInApp`, after `AuthGate` accepts a signed-in or local session. `apps/web/src/OfficeTourView.tsx` uses static room and example role data and labels the view as a demo with no real task execution. `apps/web/e2e/oidc-sign-in.spec.ts` checks that a signed-out visitor cannot reach the view and that entering it does not fetch workspace data. This browser gate is defense in depth; future office layout, presence and meeting APIs must independently resolve membership and enforce workspace RLS on every read and write. The browser's selected building, floor, room, or workspace header is never authorization evidence.

## Secrets

Secrets must be stored outside source control. Provider keys, integration tokens, signing keys, and storage credentials should be delivered through environment-specific secret stores. Local development may use `.env` files, but sample files must contain placeholders only.

On Kubernetes the Helm chart never renders a Secret and holds no credential in its values: it references Secrets created by the secret store (for example External Secrets) by name, each pod gets a ServiceAccount without an API token, and default-deny NetworkPolicies limit traffic ([Deployment](deployment.md)). The database logins are split: the migration login owns the schema, the application login is subject to RLS, the relay and maintenance roles are narrow, and only the backup login bypasses RLS. The chart also refuses to render the configurations the startup policy below refuses.

On Render (`render.yaml`, [Deploying on Render](deploy-render.md)) every secret is a `sync: false` variable entered in the Dashboard, a Render-generated value, or wired from a Render database or service; `services/api/tests/test_render_blueprint.py` fails on any literal credential. The same login split applies, with one weaker point: the migration login's URL is an environment variable of the API service (used by the pre-deploy step and removed before the API process starts), not a separate secret. Render offers no network policies and no image admission control.

On one VM (`infra/oracle`, [Deploying on one Oracle Cloud VM](deploy-oracle.md)) every secret is generated on the server by `infra/oracle/configure_env.py` from the operating system's random generator into `infra/oracle/.env` (mode 600, gitignored; never printed) or typed by the owner at a hidden prompt; `compose.yaml` holds only `${VAR}` references and `.env.example` only placeholders, which `services/api/tests/test_oracle_compose.py` asserts. The login split is stricter than on Render: the migration password reaches only the `db-init` and `migrate` one-shots, the cluster superuser password only `postgres`, `db-init` and the restore tools, the backup login (`BYPASSRLS`, `pg_read_all_data`) only the backup jobs, and Keycloak has its own login and database with `CONNECT` revoked from everyone else in both directions. Passwords reach `psql` as `\set` lines on stdin, never on a command line. Only Caddy publishes ports; PostgreSQL and Valkey sit on an internal Docker network Caddy is not attached to. The weaker points: all secrets live in one file on one machine, readable with `sudo`, and the VM builds its own images, which nothing signs. Off-site backups are encrypted on the VM (rclone `crypt`) before upload.

## HTTP Hardening

`services/api/anum_api/hardening.py` adds pure ASGI middlewares (they never buffer SSE streams). For a request the order is CORS, security headers, rate limit, body size limit, then the application.

| Control | Behaviour | Settings |
|---|---|---|
| Body size limit | `413 payload_too_large` when `Content-Length` or the streamed body exceeds the limit. `POST /api/v1/files` uploads get the larger upload limit. | `ANUM_MAX_REQUEST_BODY_BYTES` (1 MiB), `ANUM_MAX_UPLOAD_BODY_BYTES` (25 MiB) |
| Rate limit | Token bucket per client IP; `429 rate_limited` with `Retry-After`. `/health` and CORS preflights are exempt. At most 10,000 client keys are tracked (least recently used dropped). `Retry-After` is exposed to browsers through CORS. | `ANUM_RATE_LIMIT_ENABLED` (true), `ANUM_RATE_LIMIT_REQUESTS_PER_MINUTE` (600), `ANUM_RATE_LIMIT_BURST` (120) |
| Security headers | Every response: `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, `Permissions-Policy`. `Strict-Transport-Security` is added outside `local`. | `ANUM_ENVIRONMENT` |
| Interactive docs | `/docs` and `/redoc` are served only in `local` (and are exempt from the API CSP there). | `ANUM_ENVIRONMENT` |
| CORS | Only `ANUM_CORS_ORIGINS`; methods `GET`, `POST`, `PUT`, `PATCH`, `DELETE`; request headers include the file upload's `X-File-Name` and `X-Content-SHA256`; no credentials. | `ANUM_CORS_ORIGINS` |
| File links | Signed, short-lived download and preview links (HMAC keyed from `ANUM_SECRETS_KEY`), served `no-store` with a sandboxing CSP; only allow-listed file types are accepted and HTML/SVG never are ([Workspace files](files.md#downloads-and-previews)). | `ANUM_FILES_LINK_TTL_SECONDS` (300) |

Rate-limit state is in memory per process by default. `ANUM_RATE_LIMIT_BACKEND=valkey` shares it across API replicas: the token bucket runs as one atomic Valkey script on the server clock under `anum:ratelimit:<client>` keys that expire once the bucket would be full again. The call runs in a worker thread with a short timeout (`ANUM_VALKEY_TIMEOUT_SECONDS`, 0.5); if Valkey is unreachable the request is limited by a per-process bucket instead of failing or going unlimited. Client IPs come from uvicorn's proxy-header handling, which only trusts `FORWARDED_ALLOW_IPS`; see [Infrastructure](infrastructure.md).

### Model endpoints and budgets

Workspace owners choose the model `base_url` the server calls. Outside `local`/`test` the outbound guard (`anum_api/model_egress.py`) only calls public HTTPS endpoints on port 443: it refuses credentials in the URL, non-canonical IP literals and hosts resolving to loopback, private, unique-local, link-local or cloud metadata, multicast, unspecified or reserved addresses, checks at save time and on every request, connects to the address it resolved (original Host and TLS name, so DNS rebinding cannot redirect a call), never follows redirects, and the connection test returns one generic error. `ANUM_MODEL_ALLOWED_HOSTS` (comma-separated `host` or `host:port`) is the explicit operator allow-list for a self-hosted model on a private network; metadata and link-local addresses stay refused for listed hosts too. Details in [Model gateway](model-gateway.md#outbound-guard-ssrf).

The `web_search` tool calls only the operator's `ANUM_SEARXNG_URL` (a private SearXNG on the compose network); no tenant input, tool argument or saved integration endpoint changes the address, redirects are not followed, only `http`/`https` result links are returned, and the audit log keeps the query length and result count, never the query or results ([Web search](tools-and-integrations.md#web-search)).

Organization administrators (`org_admin`) can set a monthly estimated-cost and token budget for the organization and workspace owners one per workspace (`/api/v1/model-budgets`, audited); model calls are refused with `402 model_budget_exceeded` once a budget is used up ([Model gateway](model-gateway.md#monthly-budgets)).

### Startup policy

Outside `ANUM_ENVIRONMENT=local` the API refuses to start (`InsecureConfigurationError`, listing every problem) when:

- `ANUM_CORS_ORIGINS` contains `*`, a localhost or loopback origin, or any non-`https` origin;
- `ANUM_DATABASE_URL` uses the compose credentials (`anum:anum`);
- the object-storage secret, webhook key or model key is a compose default (`anum-local-secret`, `anum`, `admin`);
- Keycloak's compose admin password (`admin/admin`) is in the API's environment or `.env` as `KEYCLOAK_ADMIN_PASSWORD` or `KC_BOOTSTRAP_ADMIN_PASSWORD` (or is `anum`/`anum-local-secret`). The API never uses Keycloak's admin account and normally never sees these variables; the check catches a shared env file or a copied compose `environment` block. The Helm chart refuses any Keycloak admin credential in `config` or `extraEnv`. The Keycloak deployment itself is outside ANUM's reach, so its rotated admin password is a release-gate item;
- rate limiting is disabled or a limit is not positive;
- upload malware scanning uses ClamAV (`ANUM_FILE_SCANNER=clamav`) with `ANUM_FILE_SCAN_REQUIRED=false`, which would store files unscanned while clamd is down; the Helm chart refuses the same. In every environment `clamav` without `ANUM_CLAMAV_HOST` is refused ([Files: Malware scanning](files.md#malware-scanning));
- `ANUM_SENTRY_DSN` (optional error reporting) uses plain `http` to anything but a private service name without dots, such as `glitchtip` on the compose network ([Observability: Error reporting](observability.md#error-reporting)). A malformed DSN is refused in every environment, without echoing its key.
- the Email Center is on (`ANUM_MAILSERVER_ENABLED=true`) with a missing or IP-address mail server host, a relay service (Brevo and the like) as the SMTP host, `ANUM_MAILSERVER_SMTP_SECURITY=none`, or an empty domain or organisation allowlist; the Helm chart refuses the same ([Email Center](email.md#email-center)).
- `ANUM_FCM_SERVICE_ACCOUNT_JSON` (optional phone push) is refused when it is not a Firebase service-account JSON key (type, project, client email, a readable PEM private key, an https token URI), in every environment and without echoing the key; the Helm chart refuses it in `config` or `extraEnv` ([Notifications](notifications.md#server)).

Each deployment path checks these refusals before deploying: `infra/helm/ci/lint.sh` for the chart, `test_render_blueprint.py` for `render.yaml`, and `test_oracle_compose.py` for `infra/oracle/compose.yaml` (the API settings built from `.env.example` must pass `enforce_startup_policy`, in staging and in production with Ollama).

The API container defaults to `ANUM_ENVIRONMENT=production`, so these checks apply unless a deployment deliberately opts into `local`. Header-mode authentication outside `local` is tracked separately in Stage 2 of the [Production plan](production-plan.md).

### Web container

The web image's nginx sends a CSP of `default-src 'self'` with these exceptions: `script-src 'wasm-unsafe-eval'` and one jsdelivr folder, `cdn.jsdelivr.net/npm/@huggingface/transformers@<locked version>/dist/` (also in `connect-src`), plus `connect-src` to `huggingface.co` for the in-browser Kokoro voice (ONNX runtime loader and model weights). The CSP names that versioned path rather than the whole CDN, which serves any npm package and would let an injected tag load arbitrary script; `tests/test_render_blueprint.py` fails when the path and the version in `pnpm-lock.yaml` differ; `connect-src` also lists `ANUM_CSP_CONNECT_SRC` (the API origin) and, only in an image built with `VITE_SENTRY_DSN`, that DSN's origin for browser error reports ([Observability](observability.md#browser-errors-web-app)); `style-src 'unsafe-inline'` for React style attributes; `frame-ancestors 'none'`, `object-src 'none'`. It also sends HSTS, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` and a `Permissions-Policy` that allows only the microphone (voice) for the page's own origin.

## Scanning in CI

The **Security scans** job in `.github/workflows/ci.yml` fails the build on:

- `pip-audit --strict services/api`: known vulnerabilities in the API's resolved dependencies.
- `pnpm audit --prod --audit-level high`: high or critical advisories in production Node dependencies.
- `bandit -r services/api/anum_api services/api/migrations`: Python SAST.
- `gitleaks` (pinned release, checksum verified) over the full history of the commit under test, with `.gitleaks.toml`.
- OSV-Scanner (`v2.6.0`, built with `go install`, so the Go checksum database verifies the source) over `pnpm-lock.yaml` and the exact dependency set pip resolves for `services/api` (written to a requirements file and scanned with `--no-resolve`). Any severity fails; exceptions live in `osv-scanner.toml`.
- `cargo audit` (`cargo-audit 0.22.2`, installed with `--locked`) over `apps/desktop/src-tauri/Cargo.lock`. RustSec vulnerabilities fail the job; unmaintained and unsound notices are printed as warnings (see the table below).

Other jobs:

- **Licenses and SBOMs**: every shipped dependency (API, web, desktop, Flutter, Android) against the license policy in `scripts/licenses/policy.toml` (GPL, AGPL, SSPL, BUSL and unknown licenses fail; LGPL and other weak copyleft need a reviewed exception), a check that `THIRD_PARTY_NOTICES.md` matches the scan, and one CycloneDX SBOM per app as the `sbom` artifact. Details: [Third-party licenses](licenses.md).
- **Docker images**: Trivy (`aquasec/trivy:0.75.0`, pinned by digest) scans the built `anum-api`, `anum-web` and `anum-backup` images (every image a deploy workflow pushes) with `--scanners vuln,secret --severity HIGH,CRITICAL --ignore-unfixed`, so any high or critical vulnerability that has a fixed version, and any secret in a layer, fails the job. Fix findings in the Dockerfile (base image bump, `apt-get upgrade` / `apk upgrade`, removing unneeded packages); an unavoidable exception goes in a `.trivyignore` at the repository root with a row below. There is no `.trivyignore` today.
- **Flutter mobile**: `flutter analyze --fatal-infos --fatal-warnings` (the `flutter_lints` set plus the rules and the `strict-casts`, `strict-inference` and `strict-raw-types` language modes in `apps/mobile/analysis_options.yaml`) is the Dart static analysis, and OSV-Scanner checks the `pubspec.lock` that `flutter pub get` resolves.
- **Tauri desktop**: `cargo clippy --locked --all-targets -- -D warnings` is the Rust static analysis (on the Windows runner, which already builds the crate).

`codeql.yml` runs CodeQL `security-extended` queries for Python and JavaScript/TypeScript.

- **Deployed images**: `deploy-staging.yml` and `deploy-production.yml` scan every image they push with Trivy (same flags as above) before pushing it, generate a CycloneDX SBOM, sign the pushed digest keyless with cosign (GitHub OIDC, `id-token: write`, no stored key) with the SBOM as a signed attestation, and verify signature, signer identity (the workflow on `main`), commit annotation and attestation before `helm upgrade` deploys the images by digest. Production re-scans the promoted digests. Trivy and cosign are built with `go install` at pinned versions (checksum database verified) instead of third-party actions. Keyless signatures are public in Rekor (repository and workflow names), so staging signs only once `STAGING_DEPLOY_TARGET` is set. Details and manual verification: [Deployment](deployment.md#image-supply-chain).
- **Admission policy**: in staging and production the release namespace is labelled for Sigstore policy-controller (`policy.sigstore.dev/include=true`). Pods there run the API, web and backup images only with a keyless signature and a signed CycloneDX SBOM attestation from `deploy-staging.yml` or `deploy-production.yml` on `main` of this repository (issuer `https://token.actions.githubusercontent.com`). Images no policy matches are refused too (`no-match-policy: deny`), and the webhook fails closed. The policies are a separate, cluster-scoped chart (`infra/helm/anum-admission`) installed by a cluster admin, so the namespace-scoped deploy identity cannot remove them or relabel its namespace. The controller chart and image are pinned by digest. CI lints and schema-validates the policies and proves in kind that an image without this repository's signature is refused in a labelled namespace. The commit annotation is still checked only by the deploy job. Details: [Deployment](deployment.md#admission-policy); refusals: [Runbooks](runbooks.md#a-pod-was-refused-by-admission).

Third-party actions (anything outside `actions/*`) are pinned to full commit SHAs with the version in a comment, and `.github/dependabot.yml` proposes weekly updates for GitHub Actions, pip (`services/api`), npm (root workspace), pub (`apps/mobile`), Cargo (`apps/desktop/src-tauri`), the two Dockerfiles and the compose file, so the pins do not go stale.

## Pre-sale review (November 2026)

A review before ANUM is sold to customers and handed to an external penetration tester ([Penetration test scope](pentest-scope.md)). It covered tenant isolation, sign-in and permissions, input and output handling, secrets, the Oracle deployment and dependencies. The automated checks it added keep the findings from coming back.

### What is now checked automatically

- `services/api/tests/test_security_inventory.py` walks every API route (about 1,120). Every route must depend on an authentication dependency (`tenant_context` and its relatives) or be listed in `PUBLIC_ROUTES` with the credential that replaces a session (signature, signed link, hashed token). Every authenticated route must reach a permission check (`require_permission` and its relatives) or be listed in `SELF_SCOPED_ROUTES` with the reason it acts only on the caller's own rows. Stale entries fail too. It also checks that every narrow cross-tenant role is granted to `anum_app` `WITH INHERIT FALSE` in `infra/helm/bootstrap-database.sql`, and that no new `async def` route opens a store on the event loop (the existing ones are frozen in `tests/event_loop_store_baseline.txt`, which may only shrink).
- `services/api/tests/test_postgres_security_inventory.py` reads the migrated catalogue instead of a fixed list: every table but `alembic_version` has row-level security enabled and forced and at least one policy; every permissive policy that applies to all roles is bounded by `anum.tenant_id` (narrowing owner-only policies are `AS RESTRICTIVE`); the cross-tenant roles are NOLOGIN and nothing bypasses RLS; no function in `public` is `SECURITY DEFINER`.

### Sign-in protection

A shared Keycloak realm (the imported `anum-realm.json`, through `infra/render/keycloak_realm.py`) and `infra/oracle/keycloak-2fa.sh apply` on a running server set the same rules as self sign-up (`SIGN_IN_PROTECTION`):

- passwords of 12 to 128 characters with a lower-case letter, an upper-case letter and a digit, not the user name or the email address, not one of the last 3;
- brute-force detection on: a temporary lockout after 10 failed sign-ins, growing by a minute each time up to 15 minutes, counted over 12 hours, and a 60-second wait after two tries within one second. Lockouts are temporary, so an attacker cannot lock an owner out for good; `keycloak-2fa.sh reset-user` lifts one.

Keycloak imports the realm file only on its first start. On a server that is already running, the owner applies the rules with `bash infra/oracle/keycloak-2fa.sh apply` (it is idempotent). Existing passwords keep working; the rules apply at the next password change.

## Agent Safety

Agents must not receive raw unrestricted access to user accounts, files, or integrations. Each tool call should be mediated by the runtime, checked against policy, logged, and paused for approval when risk requires it. Prompt injection must be treated as an expected attack class, especially when agents read external content. The [Threat model](threat-model.md) maps the trust boundaries, what an injected instruction can and cannot do today, and the open gaps (approval content and binding, tool output size and provenance). SSRF through workspace model base URLs (G1) and per-tenant model budgets (G4) are closed.

### Browser research

`web.browse_page` runs a page's JavaScript in Chromium, so it is the riskiest read-only tool. Its controls ([Browser research](browser-research.md)): the browser runs in its own container with no ANUM secrets and no route to PostgreSQL, Valkey or the other services; Chromium cannot reach the network itself; every request goes through a gate that allows GET reads of public https addresses only, resolves each host once, refuses any non-public answer (private, loopback, link-local, metadata, unique-local, reserved) and dials the checked address (no DNS rebinding), checks every redirect hop, passes no cookies and refuses downloads, frames and forms. Off per workspace until an owner turns it on; audit records hold addresses and counts, never page content. Threat model row T9.

`web.act`, the [Action browser](action-browser.md), uses the same container in action mode to do browser tasks for the owner. It keeps cookies only for one task, reaches the internet only through a CONNECT proxy that dials checked public addresses on port 443, never shows saved passwords or cards to the model (handles, decrypted at the moment of typing), and stops for the owner's approval, bound to the payload hash and re-checked against the page, before anything that pays, sends, submits, signs, posts or deletes. Captchas and codes go to the owner. Threat model rows T10 to T14.

### Document vault

Identity papers, contracts and receipts ([Document vault](documents.md)): vault files are hidden from every unit of work but the vault's own by a restrictive row policy on `workspace_files`, and a private document is visible only to its owner and the people it is shared with (restrictive policy `vault_documents_private`, checked again in the API); identity and account numbers are Fernet-encrypted and listed as the last four only; every read is in the document's access log. Scanned text is untrusted data: it is matched against fixed patterns only, never sent to a model, values are validated and wait for the person to confirm them, and instruction-like text is dropped and flagged. The OCR service runs local Tesseract in its own container with no secrets but its token, no internet and no database. iPhone Shortcut tokens carry the `documents` scope only, are stored as SHA-256, re-check the owner's membership and role on every upload and can be disconnected.

## Data Protection

Tenant data should be encrypted in transit and at rest by infrastructure defaults. Sensitive fields should be minimized, redacted in logs, and excluded from analytics payloads. Telemetry follows the redaction rules in [Observability](observability.md#redaction-rules): spans carry tenant and workspace ids only, never prompts, replies, query strings, credentials or client addresses. Backups contain every tenant and are handled as described in [Runbooks](runbooks.md#backup-and-restore). Memory records should carry provenance, scope, and retention metadata.

### Screenshots and screen recording

Owner decision of 12 October 2026: the phone app blocks screenshots where the platform allows it. Android sets `FLAG_SECURE` (screenshots, recordings and the recent-apps thumbnail show nothing); iOS cannot block screenshots, so the app covers itself in the app switcher and while the screen is recorded, mirrored or shared ([Flutter mobile](mobile.md#screen-privacy)). The web app and the desktop app cannot block screenshots or screen recording: a browser page or webview has no such control, so anything shown there can be captured by the person viewing it.

### App lock on the phone

The Flutter app has an optional app lock (off by default): the phone's fingerprint, face or screen lock in front of Finance, Books and approval decisions, or the whole app, on a cold start and after a chosen time in the background. Approving or rejecting asks again when the last unlock is older than that time. It is a guard against someone holding the unlocked phone, not a cryptographic barrier: the check's result is not bound to the session token, so the server session remains the authority and a lost phone still needs its session revoked. Android adds the `USE_BIOMETRIC` permission and iOS the Face ID usage text; ANUM stores no PIN and no biometric data, only the on or off flag, the delay and the scope, in the phone's secure storage ([Flutter mobile](mobile.md#app-lock)).

## Auditability

Security-relevant events should be recorded: login, token refresh failures, tenant membership changes, role grants, integration consent, tool execution, approval decisions, memory deletion, policy changes, and administrative exports. Invitation, membership, model budget and governance changes (policy packs, role templates, approval rules, memory governance) are recorded in the append-only `audit_records` table (RLS allows select and insert only) when `ANUM_REPOSITORY_BACKEND=postgresql`; the `memory` backend keeps an in-process recorder.
