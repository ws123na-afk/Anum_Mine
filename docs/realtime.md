# Realtime

Realtime communication makes agent work understandable while it is happening. ANUM clients should receive task status, run steps, approval requests, tool results, notifications, and presence updates without polling every endpoint.

## Transport

The first implementation can use server-sent events for task streams because SSE is simple, browser-friendly, and fits one-way progress updates. WebSockets can be added when bidirectional low-latency collaboration, voice control, or presence requires it.

## Stream Sources

Realtime streams should be backed by persisted task state and NATS events. Clients should be able to reconnect and recover recent events from the API rather than losing context when a connection drops.

## Client Behavior

Clients should show clear task state: queued, running, waiting for approval, waiting for user input, completed, failed, canceled, or blocked. Approval events should be prominent and actionable. Tool execution should be visible enough to build trust without exposing secrets.

## Security

Realtime subscriptions must be authorized by tenant, workspace, and resource. Stream payloads should use the same redaction rules as REST responses.

## Implementation

`GET /api/v1/events/stream` is an SSE endpoint scoped to the caller's tenant and workspace, optionally filtered by `task_id`, resumable with `Last-Event-ID`, with `follow=false` for a one-shot replay.

Where a stream starts (November 2026):

- **No `Last-Event-ID`** (every page load of the web app, the desktop app and the phone app's command view): the stream starts at the workspace's newest event and sends only what happens from then on. Clients load the current state through the REST endpoints and treat an event as "something changed", so nothing old is needed. Before this the stream first sent the workspace's whole event history on every connect (20,000 events were 10.8 MB and 9 s), and the web app raised its notices again for events of past days.
- **`Last-Event-ID`**: the events after that one, oldest first. A cursor the workspace does not have starts at the newest event (see [Stale stream cursors](#stale-stream-cursors)).
- **`follow=false`**: a one-shot replay from the cursor (from the oldest event kept when there is none; the newest event alone when the cursor is unknown), then the stream ends.

### Stale stream cursors

A `Last-Event-ID` the workspace does not have (retention purged it, or it is another workspace's, as after a workspace switch in the same tab) starts the stream at the workspace's newest event: `list_events_after` returns that one event, so the stream's cursor becomes an id the workspace has, and every later read sees only what follows. The client gets one event it may already have shown (clients treat an event as "something changed", and the NATS-fed stream suppresses duplicates by id), never the history. Before (November 2026) an unknown cursor fell back to the oldest event, so a tab that reconnected after the retention job had purged its cursor replayed the whole history in 500-row pages. Both backends behave the same (`repository.InMemoryRepository.list_events_after`, `db/repository.SqlAlchemyRepository.list_events_after`); `tests/test_event_stream_start.py`, `tests/test_postgres_repository.py` and `tests/test_postgres_event_retention.py` cover it.

Every read is bounded: a stream fetches at most 500 events per read (`dependencies.EVENT_STREAM_PAGE_SIZE`) and, when a read comes back full, reads again from its new cursor at once, so a client that is far behind catches up page by page and no read or response chunk grows with the history. The cursor moves past every event read, also the ones a `task_id` stream does not send (such a stream used to read the whole history again every second while its task was quiet). `tests/test_event_stream_start.py` covers the start, the resume, the paging and the cursor for both bus modes.

- `ANUM_EVENT_BUS=memory` (default, and the Oracle VM): the stream polls the repository once a second, reading only the events after its cursor (`list_events_after`), so a poll stays cheap as the history grows. The read is two ordered index scans of `ix_domain_events_scope_created` (`tenant_id, workspace_id, created_at, id`, migration `0162_event_stream_retention`), one for the workspace's events and one for the tenant-wide ones, merged; before that index a poll fetched and sorted the workspace's history, because the only index on those columns had `type` before `created_at`.
- `ANUM_EVENT_BUS=nats`: each API process runs one ordered JetStream consumer on `anum.>` (deliver new) that feeds an in-process realtime hub (`services/api/anum_api/realtime.py`). A stream registers a listener for its tenant and workspace before replaying history from the repository after the `Last-Event-ID` cursor, then forwards live events; duplicates from replay overlap or at-least-once redelivery are suppressed by event id. If NATS is unavailable, or a slow listener overflows its 1,000-event queue, the stream falls back to catching up from the repository, so no event is lost to a client.

An open stream holds no database connection. Streaming routes that need the request repository (this one and `/audit/export`) take it with `Depends(repository_context, scope="function")`; the voice `ask/stream` and `look/stream` and the chat `ask` take none and read in their own short sessions in worker threads (see [Event loop](#event-loop)): FastAPI's default `"request"` scope keeps a `yield` dependency open until the response ends, which for a stream is the life of the tab. Each open tab then held a pooled PostgreSQL connection "idle in transaction"; about a dozen tabs, phones or reconnects used up the pool (5 + 10 overflow), every poll waited for a connection on the event loop, and the whole API, `/health` included, stopped answering for minutes (the "web app hangs after a short while" report on the Oracle VM, October 2026). The body reads through `list_events_for_stream`, a short session per poll, in a worker thread (`asyncio.to_thread`), never on the event loop. `tests/test_stream_sessions.py` fails if a streaming route holds a session dependency for the whole stream, and `tests/test_postgres_event_stream_pool.py` keeps more streams open than a small pool has connections and requires the API to keep answering.

A stream ends when `request.is_disconnected()` reports that its client left; uvicorn drops writes to a closed connection silently, so this check is the stream's only way out. Middleware in front of the API must therefore be plain ASGI: Starlette's `BaseHTTPMiddleware` hides the disconnect, which once left every closed SSE stream running and blocked graceful shutdown (`CorrelationIdMiddleware` is plain ASGI for this reason, covered by `tests/test_api_contracts.py`).

The CI job "Authenticated journey" (`services/api/scripts/run_journey.sh`) opens this stream as a Keycloak-authenticated user with `ANUM_EVENT_BUS=nats` and checks that a task's `task.created`, `approval.requested`, `approval.approved` and `agent_run.completed` events arrive in order, are on the `ANUM_EVENTS` JetStream stream, and are persisted.

The in-app call stream (`GET /api/v1/app-calls/stream`) rides the same bus without replaying history ([In-app calls](in-app-calls.md#signaling)). The realtime hub hands every message that passed its scope checks to its observers (`RealtimeHub.add_observer`); the call wake hub (`services/api/anum_api/app_call_wake.py`) is one, and wakes the call streams of the event's tenant and workspace on `app_call.ringing`, `app_call.updated` and `app_call.signaled`. A woken stream re-reads its calls and signals in a worker thread, in its own short session. With `ANUM_EVENT_BUS=memory`, or while NATS is down, the same events reach the wake hub in process from the committing thread (it only schedules the wake-up on the stream's loop, `call_soon_threadsafe`) and the stream keeps its 1 s / 0.25 s poll; with NATS live the poll slows to a 10 s fallback. `app_call.updated` and `app_call.signaled` are left out of `/events` and `/events/stream`. Covered by `tests/test_app_call_wake.py`, `tests/test_app_calls_off_event_loop.py` and the NATS integration test.

Isolation: the hub routes a message only to listeners whose escaped tenant and workspace tokens equal the subject's, and only after checking that the decoded event's tenant, workspace, type and `Nats-Msg-Id` agree with the subject; mismatched messages are dropped and counted. Each listener re-checks the event against its own tenant context. Tenant-wide events (no workspace) reach every workspace of that tenant only. Tests in `services/api/tests/test_event_bus.py` cover cross-tenant and cross-workspace isolation, forged subjects and hostile identifiers.

## Event history

`domain_events` holds every event a workspace produced. It is what the stream and NATS are fed from; it is not the audit trail (`audit_records`, [Security](security.md)), which is another table with its own rules.

- **Retention:** the daily retention job (`python -m anum_api.voice_retention`, step `events`; `python -m anum_api.event_retention [--dry-run]` runs it alone) deletes events older than `ANUM_EVENT_RETENTION_DAYS`. It is off by default (`0`, keep every event): the owner turns it on with a period of 7 to 3650 days (the API refuses to start on 1 to 6), so a deploy never deletes history nobody asked to lose. Nothing else deletes an event, so with the default the table and every read of a workspace's history keep growing; the stream and the lists are bounded regardless (above). 90 days is a sensible period once the owner decides.
- **What stays:** audit records, tasks, runs with every step, approvals and results are their own tables and are not touched. With `ANUM_EVENT_BUS=nats` an event the outbox relay has not published yet is kept whatever its age.
- **What goes with an old event:** its line in a task's Activity list and run log export (`GET /tasks/{id}/events`, `/export`), and its place in a stream resumed with a `Last-Event-ID` that old (such a stream resumes at the newest event, see [Stale stream cursors](#stale-stream-cursors); it does not replay the history).
- **How:** scopes are discovered as `anum_maintenance`, which may read only the tenant, the workspace and, for a [private task](tasks.md#private-tasks)'s events, whose they are (`private_to`, a user id) of events older than 7 days (policy `maintenance_event_retention`, migration `0162_event_stream_retention`; the column grant and the admission to private rows from `0163_private_tasks`; never a type, a subject or a payload). Each scope is purged as the application role inside its own tenant and workspace context, a private person's scope with `anum.user_id` set to that person (the restrictive private-task policy hides their events from every other session, so a purge without it never deleted them), 5,000 rows per transaction, and a workspace that lost events gets one audit record `event_retention.purge` with the count only. A run is idempotent and an interrupted run is finished by the next one. Covered by `tests/test_postgres_event_retention.py`.

## Event loop

The API runs one event loop per process (a single uvicorn worker on the Oracle VM). Database access is synchronous (SQLAlchemy sessions), so a store, repository or session used inside an `async def` route or an SSE body blocks every request of the process while it runs, and for as long as it waits for a pooled connection or a row lock. The rule:

- Assistant answers (`POST /api/v1/conversations/{id}/ask`, voice `ask`, `ask/stream` and `look/stream`) do every read and write in a worker thread (`asyncio.to_thread`), each in its own short unit of work, and keep no session open while the model answers. The voice routes open their unit of work inside the thread (`voice.prepare_ask_in_own_session`, which also checks the membership), instead of a request repository held across the model call.
- The budgeted model gateway (`model_budget.BudgetedModelGateway`) checks the budget and records usage in a worker thread; a stopped stream records its usage in the background. The retriever's index check and vector search run in a worker thread too.
- An SSE body never reads through the request's repository session (`list_events_for_stream`, `_store_reply`, `_store_voice_reply` and the call stream's `read_snapshot` and `settle_for_stream` open their own, in worker threads; `tests/test_app_calls_off_event_loop.py` covers the call stream's woken reads, polls and settles).
- The pool is sized for the streams and requests one user's tabs open and every wait is bounded: `ANUM_DATABASE_POOL_SIZE` (10), `ANUM_DATABASE_MAX_OVERFLOW` (20), `ANUM_DATABASE_POOL_TIMEOUT_SECONDS` (10; a request that cannot get a connection fails instead of waiting 30 s) and `ANUM_DATABASE_LOCK_TIMEOUT_MS` (10000; PostgreSQL `lock_timeout` on every API connection, 0 turns it off), so a wait for a row lock held by a stalled transaction cannot hold the process indefinitely.

Before this (October 2026, after the stream fix above) a chat question made dozens of blocking database round trips on the event loop and the voice `ask` kept a connection "idle in transaction" for the whole model call; on the Oracle VM one question in one tab stopped every other tab. `tests/test_ask_off_event_loop.py` fails if an assistant answer opens a store or unit of work on the event loop, and `tests/test_postgres_loop_responsiveness.py` (PostgreSQL, production pool settings, six open event streams, a slow model and a slow database) requires `/health` and an authenticated read to keep answering while an answer streams or an inline task runs, with no connection idle in transaction, and a Cancel during a run to answer within two seconds.

- Inline task runs (`POST /tasks/{id}/run`, retry, automations and chat tool cards) never hold a transaction or the task's row lock while the model or the tool works: they claim, plan, apply and settle in short units of work in worker threads ([Agent runtime](agent-runtime.md#inline-runs)). A run used to keep the task's `SELECT ... FOR UPDATE` lock across the model call; a Cancel of that task then waited for the lock on the event loop, the run could never resume to release it, and the API stopped answering indefinitely. The tyre grounding tool also runs with no transaction open. `POST /tasks/{id}/cancel` takes the task's row lock and writes the cancellation in a worker thread, not on the event loop, so other requests keep being answered while it waits for the database (`test_postgres_loop_responsiveness.py`). It locks the task's own approvals only (`list_task_approvals(..., for_update=True)`); until November 2026 it row-locked every approval of the workspace to expire its own, so a cancel waited for, and held up, a decision on any other task (`tests/test_postgres_tasks.py`).
- Async agent tool handlers follow the same rule: placing an approved AI phone call reads and writes the calls store, the Contacts directory and the model settings in worker threads, never across the provider call ([Phone calls](calls.md#ai-calls)).
- `repository_context` (and the identity, memory and provisioning variants) wrap plain generators, so FastAPI opens, checks membership and commits them in its thread pool. `tenant_context` reads the OIDC membership and the archived-workspace flag in a worker thread. The voice session and transcript routes are plain `def` routes.

### Worker threads

Every `asyncio.to_thread` call (the store steps of async routes, each stream poll, the background jobs) runs on the event loop's default executor. Python creates it on first use with `min(32, CPUs + 4)` threads, which is 6 on the 2-CPU Oracle VM: six slow reads, or six tabs polling a slow database, and every other store step of the process queued behind them. The lifespan's first step, `serving.use_worker_threads`, gives the loop an explicit executor of `ANUM_WORKER_THREADS` threads (thread names `anum-worker_N`). The threads mostly wait for the database, so the number follows the connection pool, not the CPU count: unset or `0` (the default), it is `ANUM_DATABASE_POOL_SIZE + ANUM_DATABASE_MAX_OVERFLOW`, 30 with the defaults above (4 to 256). An explicit `ANUM_WORKER_THREADS` is kept as an override but may not exceed that sum: the API refuses to start otherwise (`settings._worker_threads_fit_the_pool`), because the extra threads could only wait for a connection, up to `ANUM_DATABASE_POOL_TIMEOUT_SECONDS`, and then fail. The first version (November 2026) defaulted to 32 against 30 connections, so under load two workers always waited on the pool. The Helm chart mirrors the refusal (`infra/helm/anum/templates/_validate.tpl`, checked by `infra/helm/ci/lint.sh`): a `config.ANUM_WORKER_THREADS` above `config.ANUM_DATABASE_POOL_SIZE + config.ANUM_DATABASE_MAX_OVERFLOW` (10 + 20 when unset) fails `helm lint`, not the pod. Plain `def` routes do not use the executor: FastAPI runs them in AnyIO's thread pool (40 threads), bounded by the same connection pool. `tests/test_serving.py` checks the default, the override, the refusal, the executor and that the lifespan sets it before anything starts.

Shutdown: a scheduler pass runs in one of these threads and cannot be cancelled; it finishes its own transaction. `stop()` of the automation scheduler, the team reminders and the organisation lifecycle runner used to wait for that pass with no limit, so one pass stuck on the database or a provider held the whole shutdown until the process was killed. They wait at most 30 s now (`serving.wait_for_pass`), log `scheduler_pass_still_running_at_stop` with the scheduler's name and let the other stops run; the thread keeps going and is still joined on a normal exit. The outbox relay's commit wait is unchanged on purpose (a relay pass must not be abandoned mid-commit).

### Garbage collection

Once its modules are imported and FastAPI has built its routes, the API process holds about 900,000 long-lived Python objects. A full garbage collection walks all of them while holding the GIL, which stops every thread of the process, the event loop included, for 0.5 to 0.9 s on a 4-core machine. No code has to block for this: the collector runs when enough new objects have survived, so the stall lands at a random moment. It was the cause of the intermittent `test_postgres_loop_responsiveness.py` failures in CI (October 2026): one probe was slower than the rest by one such pause (`/health` 0.70 s, or `GET /conversations` 1.0 s against a 0.2 s median), with no pool, thread pool or row lock wait behind it.

The last step of the lifespan's startup, `prepare_for_serving` in `services/api/anum_api/serving.py`:

- Builds every route's state with one request no route serves (method `ANUM-WARM-UP`, path `/__anum_warm_up_routes__`), sent to the router itself, so no middleware and no endpoint runs. FastAPI builds a router's dependency graphs lazily, on the event loop, the first time a request walks past it: before this, the first request after a start took 3 to 5 s and every other request waited meanwhile.
- Collects once and calls `gc.freeze()`: everything alive at startup moves to the collector's permanent generation, so later full collections only walk objects created since then (milliseconds). Frozen objects are never collected again; what exists at startup is modules, classes, routes and settings that live as long as the process anyway.

Test servers that run without the lifespan (`tests/test_postgres_loop_responsiveness.py`) call `prepare_for_serving` themselves so they serve like production, and `tests/test_serving.py` checks the warm-up (every route built, no endpoint run) and that the lifespan calls it.

### Commit order

A request's unit of work commits, and publishes its events, before the response starts. FastAPI closes a `yield` dependency with its default scope (`"request"`) only after the response has been sent, so a client could read a `200` and send its next request before the write was committed. The authenticated journey hit this in CI (runs 38814995240 and 39113185705): `PUT /api/v1/onboarding` answered 200, the SSE request that followed checked the membership on another connection before the onboarding transaction had committed, and was refused with `403 Active workspace membership required`. `repository_context`, `provisioning_repository_context`, `identity_repository_context` and `memory_repository_context` are therefore plain wrappers around their generators resolved with `scope="function"` (`services/api/anum_api/dependencies.py`); every route keeps `Depends(repository_context)`. A side effect: background tasks a route schedules run after the commit and see its rows. `tests/test_commit_before_response.py` checks the order against the in-memory store and, with PostgreSQL, that the membership onboarding creates is committed before the 200 and admits the next request.

Every route (pre-sale review P7, November 2026): no `async def` route opens a store or unit of work on the event loop. `tests/test_security_inventory.py` checks each route's own body (a nested plain function counts only when the async body calls it directly; one handed to `asyncio.to_thread` runs in a worker thread) and `tests/test_routes_off_event_loop.py` wraps every store opener on the whole app and fails if one runs on the loop. The patterns:

- A route that awaits nothing is a plain `def` route: FastAPI runs it, its dependencies and its database work in its thread pool. A function another module awaited (`email_api.request_send_approval`, `mailbox.api.send_draft`, `learning_api.record_feedback`) is now called through `asyncio.to_thread`; setup plans call route functions through `_run`, which accepts a plain value.
- A route that reads the request body or calls a provider, a model, GitHub or Meta stays `async` and does each store step in `asyncio.to_thread`: read, then the outside call with no store open, then write and audit. The request repository may be used inside those threads (one at a time, never two at once).
- Home's sources (`home._call`) run in a worker thread unless the source is itself `async`.
- The retrieval indexer (`retrieval.RetrievalIndexer`) runs every store call in a worker thread. Files, knowledge notes and collection re-indexes index after their rows committed, through a store that opens a short unit of work per call (`retrieval_api._ShortUnitStore`), so no transaction is held while the embedding model answers. A memory created inside a memory route's transaction (`index_memory_note`) is still indexed in that transaction, under a savepoint, with each step in a worker thread.
- The marketing publisher claims, records failures and records results in worker threads, with only the platform call on the loop.

Calling is the other way onto the loop (reliability audit, November 2026). The checks above look at who opens a store. FastAPI opens `Depends(repository_context)` in its thread pool, but the body of an `async def` route runs on the event loop, so `repository.list_tasks(...)` there is SQL on the loop: every user waits while it runs, waits for a pooled connection or waits for a row lock. 88 routes did this, among them `GET /tasks`, `/tasks/summary`, `/events`, `/approvals`, the workspace member and invitation routes, the audit log, commands, autonomy and onboarding.

- 77 of them awaited nothing and are plain `def` routes now.
- `POST /workspaces` is a plain `def` route too (its only await was the plan check in a thread). `POST /tasks` stays `async` because `office_assign_api` and `executive_pa` await `main.create_task`; its agent check, plan check, insert and event run in one worker thread. `POST /memories` and `POST /platform/billing/run` keep their awaited step (indexing, the billing run) and run every store step before and after it in `asyncio.to_thread`, one at a time, in the request's unit of work.
- `tests/test_security_inventory.py` (`test_no_new_async_route_calls_its_repository_on_the_event_loop`) reads every `async def` route: a method call on a repository or store parameter, or handing one to a plain function, in the async body or in a nested function the body calls directly, fails the test. An awaited `async` helper is the other baseline's business (below). `tests/test_routes_off_event_loop.py` also wraps every method of the in-memory repositories and calls one route per module: a call on a running loop fails it.
- Left, frozen in `tests/repository_on_loop_baseline.txt` (may only shrink): `POST /executive-pa/invoke` reads and writes through the request repository in helpers it calls on the loop and needs its own pass; `GET /home/summary`, `GET /home/insights` and `POST /retrieval/index` only wrap the repository in an object on the loop (`home._scope`, `retrieval_api._workspace_store`), and every query behind it runs in a worker thread.

The `async` helpers routes and jobs await (November 2026, after P7) follow the same rule: every store step runs in `asyncio.to_thread` in its own short unit of work, and nothing stays open while a provider, a model or a tool works.

- Email provider helpers (`email_inbox.sync_account`, `access_token`, `fetch_body`, `save_provider_draft`, model triage and drafts, the email tools) read and write the mailbox in worker threads; only the provider and model calls wait on the loop. So do calendar sync (`calendar_sync.sync_connection`, `attach_and_push`, `remove_at_provider`, the invitations tool), the WhatsApp tools and triage, the mail AI tools, the Email Center send, delete and settings tools, the mailbox forwarding rules and `mailbox.service.on_server`'s health writes. `ToolRegistry.execute` reads the contact suppression list in a worker thread.
- Governed tool execution: `AgentRuntime.finish_execution` audits and settles the run in a worker thread. A caller that committed the `executing` checkpoint first uses `runtime.finish_execution_in_units`: the tool runs with no transaction open, then the audit record and the run's outcome are written in a new short unit. The WhatsApp send route and `delivery.request_delivery` (invoice and report emails) work this way: plan and policy in one unit, the tool with none, the outcome in another.
- Routes that call a provider, a model or a tool take `units: UnitsOfWork = Depends(units_of_work)` instead of `repository_context` and run each store step with `dependencies.run_in_unit` (its own unit, membership checked, in a worker thread). The email routes, calendar connect, sync and event routes, the mail AI routes, WhatsApp send and drafts, the invoice email and the tyre report delivery do, and so do the Email Center page routes (mailbox check, flags, move, delete for good, new drafts, attachments), marketing (OAuth callback, disconnect, publish now, retry, schedule, the weekly report delivery), developer mode (projects test and workflow install, requests list, read, create, cancel and merge approval, and the background watcher's refresh), tyre sync and connection test, the WhatsApp account save, check and test, the sales quote WhatsApp delivery, Business support replies, report sharing and saving to Files, the integration setup check, task cancel and bulk task actions. The helpers they await take the `UnitsOfWork` too (`marketing.service.finish_oauth`, `revoke_account`, `report_delivery.deliver`, `support_channels.request_*_reply`, `developer._refresh`); there is no adapter for a held unit any more.
- `tests/test_helpers_off_event_loop.py` follows each of those helpers into the plain functions it calls and fails if one opens a store on the loop; it also runs the email, calendar and WhatsApp send paths with every store opener guarded. A second check freezes the `async` routes that still keep the request's unit of work open across a non-thread await in `tests/request_unit_across_await_baseline.txt` (44 when it was added, 10 now); the list may only shrink.
- The approval decision (`POST /approvals/{id}/approve` and `/reject`) and `POST /agent-runs/{id}/resume` run the tool with no transaction open, the way inline runs do: one short unit locks the task and the approval (`FOR UPDATE`), makes every check (pending, expiry, the payload hash the client displayed, routing and governance, the two-person rule, the integration target, tool policy), records the decision with its event and audit record and commits the run as `executing`; the tool then runs with no transaction and no row lock; a new unit re-checks the claim (still that `executing` checkpoint) and records the outcome (`inline_runs.execute_committed`). Single use holds without the lock: the decision is committed before the tool runs, so a second approve finds it decided (409). A Cancel while the tool runs is kept and the approve answers 409 (the tool's audit record stays); a tool that raises fails the run, and the approval stays used. With the durable runtime the dispatcher is signalled after the commit. `tests/test_approval_tool_off_transaction.py` covers these cases.
- `POST /autonomy/actions/{id}/undo` follows the same pattern (November 2026, migration `0165_autonomy_undo_claim`): one short unit makes every check and commits the action's `undo_claimed_at`; the compensating tool runs with no transaction and no row lock; a new unit locks the row, checks the claim is still this request's and records the outcome. Single use held through the row lock before, so a second undo waited on it for as long as the tool took; now it finds the committed claim and answers 409 at once ([Autonomy](autonomy.md#activity-and-undo)). `tests/test_autonomy.py` and `tests/test_postgres_autonomy.py` run a second undo while the first's tool call is in flight.
- Failure audit records written before a refusal (a mailbox check, a developer dispatch or cancel, a tyre sync, a WhatsApp test) now commit in their own unit in PostgreSQL too, as they already did on the in-memory backend; before, raising the refusal rolled them back with the request transaction.

Still in the baseline, and why:

- `GET /events/stream`: the static check sees the stream body's awaits; the route takes its repository with `scope="function"`, which is closed before the stream starts (see [Implementation](#implementation)).
- `GET /home/summary`, `GET /home/insights`, `POST /home/insights/{key}/dismiss` and `/snooze`: Home's sources share the request repository; `async` sources need their own units first.
- `POST /executive-pa/invoke`: dispatches to many read and write helpers that take the request repository; it needs its own pass.
- `POST /memories` and `POST /retrieval/index`: a memory note is indexed in the transaction that created it, under a savepoint, on purpose (see the retrieval bullet above).
- `POST /platform/billing/run`: billing is being changed in parallel; left for that work.

The pool and lock timeouts above bound those waits.
