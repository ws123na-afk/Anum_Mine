# Tools and Integrations

Tools are the controlled actions ANUM can perform. Integrations connect ANUM to external systems such as GitHub, calendars, email, storage, CRMs, databases, and internal APIs. Every tool call must pass through the runtime.

## Integration Types

- REST integrations for standard web APIs.
- MCP integrations for structured tool ecosystems.
- Webhooks for inbound events.
- Browser or desktop tools for user-local actions in later phases.
- Internal tools for ANUM platform operations.

## Tool Contract

A tool should declare name, description, input schema, output schema, required permissions, risk level, timeout, retry policy, idempotency behavior, and audit fields. Tool results should distinguish successful output, recoverable failure, blocked action, and partial completion.

## Consent and Credentials

Integration credentials should be scoped to tenant, workspace, user, or agent. The system should show what access an integration has and allow revocation. Agents should never see raw secrets.

## Workspace Configuration

Integrations are defined by the operator's Settings; this deployment has exactly these: PostgreSQL (`ANUM_DATABASE_URL`), Keycloak (`ANUM_KEYCLOAK_ISSUER`), NATS (`ANUM_NATS_URL`), Temporal (`ANUM_TEMPORAL_TARGET`), Valkey (`ANUM_VALKEY_URL`), S3 object storage (`ANUM_S3_ENDPOINT`), SearXNG web search (`ANUM_SEARXNG_URL`) and the external REST webhook behind `external.action` (`ANUM_EXTERNAL_WEBHOOK_URL`). A workspace never changes where ANUM connects (SSRF): probes and tools always use the operator-configured endpoint.

- **Health (`GET /api/v1/integrations`, any member).** Each entry has `status` (`connected`, `degraded`, `disabled`), `detail` (only the exception class on a failure, never a message that could carry hosts or users), `latency_ms`, `environment_variable`, `available` (the operator configured it; when false no workspace switch can turn it on, and the detail says what to set), `enabled` (this workspace's switch), `remediation` (how to fix a degraded or unused integration), `checked_at`, and `last_error` with `last_error_at`, kept after the service recovers. Every call records the result per workspace (best effort: a failed write is logged and the live answer still returns). Probes run without holding a database session and time out after 2.5 seconds.
- **Test connection (`POST /api/v1/integrations/{id}/test`, workspace owners: `organization:manage`).** Probes one integration now, records the result and writes an `integration.tested` audit record (`outcome` `failed` when it is degraded). An integration turned off for the workspace is reported `disabled` and not probed.
- **Switch (`GET|PUT /api/v1/integrations/{id}/configuration`, owners).** `enabled: false` turns an integration off for this workspace (audited as `integration.configured`); the card then says "Turned off for this workspace by an owner" and how to turn it back on. `enabled: true` never turns on an integration the operator did not configure. The stored `endpoint` is informational only and is never connected to; the web no longer offers to edit it.
- **Workspace credentials (`PUT|DELETE /api/v1/integrations/{id}/credential`, owners).** Only the external REST webhook accepts one (`accepts_workspace_credential`); every other integration answers `409` naming the operator setting it uses. The body is `{"secret": ...}`: 12 to 4096 printable ASCII characters without spaces (it is sent as a bearer token). It is stored only as Fernet ciphertext with `ANUM_SECRETS_KEY` ([Security](security.md)), never returned or logged; the API shows `workspace_credential` with `configured`, a `hint` (its last four characters), `updated_by` and `updated_at`. Setting and removing it are audited (`integration.credential_set` with `replaced`, `integration.credential_removed`), never with the value. `python -m anum_api.rotate_secrets` re-encrypts these credentials too ([Runbooks](runbooks.md#rotating-anum_secrets_key)).
- **Storage.** With `ANUM_REPOSITORY_BACKEND=postgresql` the switches live in `integration_configurations`, the health history in `integration_health_checks` and the credentials in `integration_credentials` (migration `0030_integration_health`), all keyed by tenant, workspace and integration under forced RLS ([Multi-tenancy](multi-tenancy.md#control-plane-stores)); audit records are written in the same transaction. `anum_maintenance` may only see which workspaces hold a credential, for rotation.
- **Clients.** The web Integrations page (`apps/web/src/IntegrationsView.tsx`) lists degraded integrations first with a summary line, and on each card the status, detail, last check, last error, a "How to fix" box and, for the webhook, where its token comes from. Owners get Test connection, the switch and the token form (password field, replace, remove with confirmation); members see the same health and a notice that only workspace owners can change integrations. Flutter Resources > Services shows the status, how to fix and the last error (`apps/mobile/lib/features/workspace/resources_screen.dart`). Tests: `services/api/tests/test_integration_workspace_state.py`, `test_postgres_integration_state.py`, `apps/web/test/catalog.test.ts`, `apps/web/e2e/integrations.spec.ts`, `apps/web/e2e/integrations-manage.spec.ts`, `apps/mobile/test/skills_resources_test.dart`.

## Connection Setup

The health list above covers the services the deployment runs on. **Connection setup** (`services/api/anum_api/integration_setup.py`) covers every integration an owner connects: AI model, server voice, recording transcription, web search, Gmail, Outlook and Zoho, WhatsApp, Zoom and Teams, phone push, notification email (SMTP), Google and Apple sign-in, error reporting, file storage, the outbound webhook, the five marketing apps, sales channels, the fleet data source and developer mode. The owner runbook for each is [Connecting integrations](integrations-setup.md).

- **`GET /api/v1/integrations/setup`** (any member with `integration:read`). Each item has `id`, `group`, `status` (`connected`, `ready` = the server is set up and an account still has to be connected, `not_configured`, `error` = a half-done setting or a failing account), `connect_view` (the web view where it is connected), `connections` and `failing` (accounts in this workspace, counted in the caller's tenant scope under RLS, and only for modules the caller can already read), `doc` (the runbook anchor) and `checkable`. `missing` (setting names) and `redirect_urls` (the exact callback URLs to register, built from the server's own settings) are filled only for workspace owners (`organization:manage`) and organization administrators; `can_view_setup` and `can_check` tell the client which. The answer never holds a setting's value. A module that fails to answer marks only its own item `error` and is logged with the error class.
- **`POST /api/v1/integrations/setup/{id}/check`** (organization administrators with an active membership; anyone else `403`). Opens a TCP connection, with a 2.5 second deadline, to the host the operator configured for that integration (the provider's fixed API host, the model or speech base URL, the SMTP host, the DSN host, the S3 endpoint or the webhook host); nothing a tenant sends chooses the host, and nothing is posted. `404` for an unknown id, `409` while it is not configured or has nothing to reach (commerce, fleet data and sign-in are checked in their own views). The result says `reachable`, `latency_ms` and only the error class in `detail`, and is audited as `integration.setup_checked` (`outcome` `failed` when unreachable).
- **Web.** The top of **Integrations** (`apps/web/src/ConnectionSetup.tsx`, `lib/integrationSetup.ts`; `#connections` opens it): a summary, a filter (all, needs setup, connected) and search, rows grouped by kind with the state, one sentence on what to do next, the cost, **Open <view>**, **Setup guide** (the runbook section), the missing settings and callback URLs with **Copy** for owners and organization administrators, and **Check connection** for organization administrators. Loading, error with **Try again**, permission denied, empty and no-match states; English and Arabic. Tests: `services/api/tests/test_integration_setup.py`, `apps/web/test/integrationSetup.test.ts`, `apps/web/e2e/connection-setup.spec.ts`.

## External REST Webhook

`external.action` (risk `high`, so every call waits for an approval) posts to `ANUM_EXTERNAL_WEBHOOK_URL` through `RestToolAdapter` (host allowlist of that one host, capped and uncompressed responses, one overall deadline). Without the URL it answers from a built-in mock and the integration reports "Not configured". The adapter reads the caller's workspace token first, then `ANUM_EXTERNAL_WEBHOOK_API_KEY`, and sends no `Authorization` header when neither exists; it decrypts the token in the caller's tenant scope at call time. When an owner turned the integration off for the workspace the tool returns `blocked` ("turned off for this workspace") before any request. The health check only opens a TCP connection to the host, because posting would run the action.

## Web Search

`web_search` is a read-only agent tool backed by a self-hosted [SearXNG](https://docs.searxng.org/) (`anum_api/web_search.py`). It is an ordinary registered tool, so every call takes the runtime's normal path: the planner proposes it, `ToolPolicy` decides (risk `low`, so no approval unless a workspace or organization rule asks for one; a policy pack can deny it), the run records the proposal and result steps, and the call is audited.

- **Configuration (operator only).** `ANUM_SEARXNG_URL` is SearXNG's base URL on the internal network (`http://searxng:8080` in `infra/docker/compose.yaml` and `infra/oracle/compose.yaml`). Empty means the tool is not registered at all, so no skill can select it, and the `searxng` entry in `GET /api/v1/integrations` is `disabled` with "Web search is off: set ANUM_SEARXNG_URL ...". A malformed value (not absolute http(s), credentials, a query) does not stop the API: the tool stays off and the health entry says what is wrong. `ANUM_WEB_SEARCH_TIMEOUT_SECONDS` (default 8, at most 30), `ANUM_WEB_SEARCH_MAX_RESULTS` (default 5, at most 20) and `ANUM_WEB_SEARCH_SAFE_SEARCH` (0 off, 1 moderate default, 2 strict) tune it. On Kubernetes set the URL through `extraEnv`; Render has no SearXNG, so the tool stays off there.
- **No SSRF.** The request always goes to `<ANUM_SEARXNG_URL>/search?format=json`. Nothing a tenant sends changes it: tool arguments other than `query` are ignored, and an endpoint a workspace owner saves under Integrations is never connected to (as for every integration). Redirects are not followed.
- **Per-workspace switch.** A workspace owner can turn the `searxng` integration off (`PUT /api/v1/integrations/searxng/configuration` with `enabled: false`, or the Integrations page). The tool then refuses before any request, the run fails with "Web search is turned off for this workspace", and the health entry says "Turned off for this workspace by an owner."
- **Query and results.** The query is the user's own prompt (whitespace collapsed, at most 400 characters), never retrieved text or model output (threat model G5). One overall deadline covers connect, send and read; the body is read up to `ANUM_TOOL_RESPONSE_MAX_BYTES` with identity encoding only (a larger or compressed answer fails the call). Results keep `title`, `url` and `snippet` (content), at most the configured number, duplicates removed, titles and snippets cut to 300 and 600 characters; only `http` and `https` links are kept (`javascript:`, `data:`, `ftp:` and the rest are dropped). The output is untrusted tool data (G3) and reaches prompts only through `tool_output_prompt_block`.
- **Failures.** A timeout, an HTTP error, an unreachable or unreadable service fails the run with a message naming the cause ("Web search timed out after 8 seconds.", "The search service answered HTTP 429."); an empty or overlong query is refused without a request.
- **Audit.** Each call writes a `tool.call` audit record (target `web_search`, outcome `succeeded`, `failed` or `blocked`) with `query_length`, `result_count`, `dropped_results`, the target host and the outcome code. Never the query text and never the results. Any tool can do the same by setting `ToolResult.audit_metadata` (counts and outcomes only); the runtime records it in the caller's tenant scope.
- **SearXNG itself** (`infra/searxng/settings.yml`): JSON format on, bot limiter off (it serves the API alone on an internal network and would otherwise need Valkey), no public-instance mode, no image proxy, metrics off, engine timeouts below the API deadline. The secret key comes from `SEARXNG_SECRET` (generated into `infra/oracle/.env`; a development placeholder locally). No published port and no Caddy route; 512 MB memory limit.
- **Clients.** The web Integrations page shows the `searxng` card with its health and whether "Agent tool web_search" is available, degraded or unavailable; owners switch it per workspace there (`apps/web/src/IntegrationsView.tsx`, `apps/web/e2e/integrations.spec.ts`). Tests: `services/api/tests/test_web_search.py`.

## WhatsApp Business

The WhatsApp inbox is a per-workspace integration with Meta's WhatsApp Cloud API: an inbound webhook verified with the app secret, encrypted per-workspace credentials, and five governed agent tools (`list_whatsapp_conversations`, `read_whatsapp`, `draft_whatsapp_reply`, `send_whatsapp`, `send_whatsapp_template`). Sending is always a tool call through `ToolPolicy` and approvals by risk. See [WhatsApp Business inbox](whatsapp.md).

## Delivery

Sending something ANUM produced to a person outside it (a tyre report by email or WhatsApp today) uses one generic path, `anum_api/delivery.py`, never a connector called directly:

- **Registering.** A connector that can deliver registers a tool whose `ToolDefinition.delivery_channel` names the channel (`email`, `whatsapp`). `GET /api/v1/tyre/delivery-channels` lists what is connected; with nothing registered, features say "No email integration is connected" and keep the item downloadable.
- **Deciding.** `request_delivery` plans the channel's tool call as an ordinary task run (task, run, proposal step, checkpointed call) and lets `ToolPolicy` decide it. Delivery tools are expected to be `high` risk, so the run waits for an approval bound to the payload hash; a governance deny blocks it; the runtime executes the approved call exactly as approved.
- **Arguments.** `{"to", "subject", "text", "attachments"}`. Attachments are references, not bytes: `{"kind", "id", "format", "filename", "content_type", "sha256", "size_bytes"}`. The tool calls `delivery.resolve_attachment(reference, context)` in the same tenant context to get the bytes; it raises if the item is gone or its SHA-256 differs from the approved reference, so what is sent is what was approved. Features register a resolver per kind (`tyre_report`: a report's frozen content rendered as PDF or CSV).
- **Not yet a channel: the inbox and WhatsApp send tools.** `send_email` (`email_inbox.py`) sends an approved reply draft: it needs `draft_id`, `account_id` and `from`, and `OutgoingMessage` carries no attachments. `send_whatsapp_template` (`whatsapp.py`) sends a Meta-approved template with text parameters to an existing conversation (`conversation_id`, `to` = that conversation's number), carries no document, and is `medium` risk with owner-chosen templates sent without approval. Neither accepts `{to, subject, text, attachments}`, so marking either as a delivery channel would plan calls that fail only after someone approved them, and the template tool would loosen the approval rule. Each needs its own delivery tool first: a new-message email send with MIME attachments (Gmail raw message, Graph `attachments`), high risk; a WhatsApp document send (media upload, then a `document` message), high risk. Until then `delivery-channels` lists nothing and reports are downloaded.
- **Tests:** `services/api/tests/test_tyre_api.py` (a fake high-risk email tool: nothing is sent before approval, the approved call receives the PDF).

## MCP Strategy

MCP should be supported as an integration protocol, not as the entire runtime. ANUM can call MCP servers through mediated adapters while still applying tenant policy, approvals, audit logging, and tool schemas.

## Now

Support a small internal tool set, one external REST integration, one MCP-style adapter path, private web search through SearXNG, credential metadata, and approval-aware execution.

## Later

Add per-integration sandboxes, webhook subscriptions, OAuth flows, rate-limit dashboards, organization-level connector policies, and workspace credentials for more integrations (today only the external REST webhook accepts one). Not built: a tenant cannot add a new integration endpoint of its own; integrations come from the operator's Settings.
Add integration catalogs, per-integration sandboxes, webhook subscriptions, OAuth flows, rate-limit dashboards, and organization-level connector policies.
